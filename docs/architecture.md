# CodeArena System Architecture Specification

## 1. Executive Architecture Overview

CodeArena is a production-grade coding contest platform designed around one core engineering challenge:
> **Accept arbitrary code from strangers, execute it safely with strict sandboxed resource limits, judge it fairly and deterministically, and push verdicts and ICPC contest standings in real-time under concurrent load.**

                       ▼         │
                   ┌────────────────┐

                   ┌───────▼────────┐

## 2. Core Architectural Principles & Invariants

1. **PostgreSQL is the Sole Source of Truth:**
   - Redis is an operational cache and speed layer (sorted sets for leaderboard, token buckets for rate limiting, pub/sub for cross-node WebSocket messaging).
   - If Redis is flushed or destroyed, all contest scores and standings can be deterministically recomputed from Postgres.

2. **Strict Isolation of Untrusted Execution:**
   - The API process **never** compiles or executes user code.
   - Only judge workers (`apps/worker`) have access to Docker Engine.
   - Workers execute user code exclusively within heavily restricted, non-networked, non-root, read-only Docker containers.

3. **Idempotent State Transitions:**
   - A BullMQ job can be redelivered if a worker stalls or terminates unexpectedly.
   - Finalization is guarded by a conditional SQL `UPDATE` inside an advisory-locked transaction.
   - Standings are **recomputed from raw submissions**, never incrementally incremented.
   - Side-effects (writing to Redis sorted sets, publishing WebSocket events) are idempotent and run after commit, even on redelivered jobs.

4. **Time Invariant:**
   - Contest time rules (start/end window, penalty calculations) strictly use the submission's server-receive timestamp (`createdAt`) generated by PostgreSQL.
   - Client clocks and queue delays **never** affect a contestant's penalty.

5. **Security Invariant:**
   - Hidden test cases and other users' source codes are strictly forbidden from leaking to client responses.

## 4. End-to-End Submission & Judging Lifecycle

```text
1. Client POST /api/v1/submissions
   └─ Validates: JWT Auth, allowed language, source size <= 64KB, contest active window, rate limit.
2. API inserts record into PostgreSQL:
   └─ status = 'QUEUED', createdAt = now() (Postgres server time).
3. API enqueues job into BullMQ queue ('judge_submissions'):
   └─ jobId = submissionId (idempotent deduplication at enqueue time).
4. API responds immediately: HTTP 201 Created { id, status: 'QUEUED' }.
5. Worker pulls job from BullMQ:
   ├─ Loads submission & test cases from PostgreSQL.
   ├─ If compiled language (C++, Java):
   │   ├─ Updates status = 'COMPILING' and emits event.
   │   └─ Executes compilation inside sandbox. On error: status = 'COMPILATION_ERROR'.
   ├─ Updates status = 'RUNNING' and emits event.
   ├─ Iterates through test cases:
   │   ├─ Mounts submission workspace as read-only.
   │   ├─ Executes binary/script with resource caps (time, memory, CPU, PIDs, /tmp tmpfs).
   │   ├─ Normalizes outputs (\r\n -> \n, strip trailing whitespace & blank lines).
   │   └─ Stops on first failure (fail-fast) or completes all.
   ├─ Begins PostgreSQL transaction:
   │   ├─ Guarded UPDATE submission SET status = :verdict, timeMs = ..., memoryKb = ...
   │   │  WHERE id = :id AND status IN ('QUEUED', 'COMPILING', 'RUNNING');
   │   ├─ If affected rows == 1 and contestId is present:
   │   │  ├─ Acquire advisory lock on (contestId, userId, problemId)
   │   │  └─ Recompute ContestProblemResult from all user submissions for this problem ordered by createdAt.
   │   └─ COMMIT.
   └─ Post-Commit Idempotent Actions:
       ├─ Recompute user's contest leaderboard score from Postgres.
       ├─ ZADD leaderboard:{contestId} score userId.
       └─ Publish events to Redis: submission.updated, leaderboard.updated.
6. NestJS Realtime Gateway receives Redis Pub/Sub event and broadcasts to:
   ├─ Room user:{userId} (submission verdict)
   └─ Room contest:{contestId} (leaderboard delta)
```

## 5. Scoring & Leaderboard System

### 5.1 ICPC Scoring Rules
- **Ranking:** Primary: Number of problems solved (descending). Secondary: Total penalty time (ascending). Tie-break: Earlier time of the last accepted submission.
- **Penalty Calculation:**
  $$\text{Problem Penalty} = \text{Minutes from contest start to 1st AC} + (\text{Penalty Minutes} \times \text{Wrong Attempts before 1st AC})$$
- Wrong attempts on unsolved problems incur **zero** penalty.
- `COMPILATION_ERROR` and `INTERNAL_ERROR` are **never** counted as wrong attempts.
- Submissions created after a problem is already solved do not alter the score.

### 5.2 Redis Sorted Set Representation
- Key: `leaderboard:{contestId}`
- Value: `userId`
- Numeric Score:
  $$\text{Score} = (\text{Solved Count} \times 10,000,000) - \text{Total Penalty Minutes}$$
- High score indicates superior rank.
- Fully rebuildable from `ContestProblemResult` in PostgreSQL at any time.
